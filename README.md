# swarm-bench

**1体 vs 10体 vs 100体。台数を増やすと、本当に良くなるのか。**

掲示板型マルチエージェントで worker を増やしたとき、品質・コスト・所要時間がどう変わるかを調べる。

> ## 先に読むこと
>
> **このリポジトリが出す数字はモデルによる推計であって、実測ではない。**
>
> 実際の LLM を 100 体起動して測るのは高くつくうえ、1 回の結果はタスク依存で大きくぶれる。
> そこでまず「台数を変えたとき、**構造として**何が起きるか」を調べ、
> そのうえで実際の `board.jsonl` からパラメータを較正する。
>
> **実測 → 較正 → 外挿** の順で使うこと。モデル単体の数字を「100 体ならこうなる」と外に出してはいけない。

**台数と速さは逆 U 字になる。** 既定パラメータでは 16 体が頂点で、
そこから先は増やすほど**遅くなり、かつ高くなる**。

記事の「1000 体起動とかもできちゃいそう」は技術的には正しいが、
**1000 体が 16 体より良い結果を出すとは限らない**、というのがこの掃引の示唆。

一方で見落としてはいけないのは、**16 体は 1 体よりコストも安い**（0.38 倍）こと。
速く終わる＝掲示板を読み直す回数が減る＝総トークンが減るため。
「並列化すると高くつく」は、台数が適正域にある限り成り立たない。

## 実ボードで較正してみた（2026-11-16）

ローカルの `qwen2.5:7b-instruct` で実際に群れ（worker 2 + verifier 1）を走らせ、
得られた `board.jsonl`（同梱: `data/real-board-ollama-qwen7b.jsonl`）で較正した。

```
1 本のボード / 38 投稿 / 6 ラウンド
  verify_result  pass 0 / needs_changes 0 / fail 0
  done 0 / assign 9 / verifier 1 体

推定パラメータ:  --coordinatorCapacity 3
注意: verify_result が 1 件も無いため pDefect を推定できません
```

### 較正で結論が逆転した

既定値（監督の帯域 12）と、実測値（3）での掃引を並べる。

| worker | 既定のラウンド | 既定の速度 | **実測のラウンド** | **実測の速度** |
|-------:|-------------:|----------:|----------------:|-------------:|
| 1 | 69.1 | 1x | 69.1 | 1x |
| 4 | 24.4 | 2.83x | **31.3** | **2.21x** |
| 16 | 14.9 | 4.65x | 41.7 | 1.66x |
| 64 | 23.1 | 3.00x | 62.8 | 1.10x |
| 100 | 28.0 | 2.47x | **73.2** | **0.94x** |

| | 較正前 | 較正後 |
|---|---:|---:|
| 費用対効果が最良 | 16 体 | **4 体** |
| 速度の飽和点 | 16 体 | **4 体** |
| 100 体の速度 | 2.47 倍速 | **0.94 倍（1 体より遅い）** |
| 100 体のコスト | 0.70 倍 | **1.23 倍** |

**較正しなければ「16 体で回せ」と答えていた。実測は「4 体」だった。**
逆 U 字の頂点は監督の帯域でほぼ決まる、という README の記述が実データで裏づけられた形になる。
そして実測の帯域では、**100 体は 1 体より遅く、かつ高い**。

### 7B モデルは終端の型を出せなかった

38 投稿の内訳は `assign` 9 / `progress` 14 / `verify_request` 12 / `note` 3。
**`done` と `verify_result` はゼロ。**

- worker は `progress` しか出さず、一度も「終わった」と言わなかった
- verifier は `verify_request` を 5 回出し（うち 1 回は自分宛）、判定を一度も下さなかった
- coordinator は 2 回、合格ゼロのまま完了を宣言しようとして却下された

掲示板のプロトコル検証自体は PASS している（形式は守れている）。
守れなかったのは**役割の契約**のほう。状態機械を前に進める型を出せないので、
`assign → progress → verify_request → …` を延々と回り続ける。

> **示唆**: 掲示板型は小さいモデルでも「形式上は」成立するが、
> **判定を下せるモデルを verifier に置かないと前に進まない**。
> 役割別モデル指定（`modelFor`）で verifier だけ上位モデルにする設計には、根拠がある。

### 較正器は分からないことを埋めなかった

`verify_result` がゼロだったため、較正器は `pDefect` の推定を拒否し、
「推定できません」と明示した。見逃した欠陥は定義上ボードに現れないので、
ここで適当な値を埋めるとモデル全体が嘘になる。この挙動はテストで固定してある。

## モデルに入れている 5 つの効き目

| # | 効き目 | 何が起きるか |
|---|--------|------------|
| 1 | **Amdahl** | 直列にしか進まない部分は台数を増やしても縮まない |
| 2 | **監督の帯域** | coordinator が 1 ラウンドに捌ける割当・回答に上限がある |
| 3 | **検証の帯域** | verifier が 1 ラウンドに検証できる件数に上限がある |
| 4 | **混線** | 台数が増えるほど確認・受け渡しが増え、1 件あたりの完了率が落ちる |
| 5 | **掲示板の肥大** | 投稿が増えるほど全員のプロンプトが伸び、1 ターンの単価が上がる |

逆 U 字の頂点がどこに来るかは、**2（監督の帯域）と 4（混線）でほぼ決まる**。
この 2 つは環境によって大きく違うので、**較正しないと頂点の位置は信用できない**。

各効き目が実際に効いていることはテストで固定している（直列 90% なら速くならない、
監督の帯域を絞れば遅くなる、など）。

## 較正する

実際に走らせた `board.jsonl` からパラメータを推定する。

```bash
node src/cli.mjs calibrate runs/*/board.jsonl
```

```
1 本のボード / 11 投稿 / 7 ラウンド

観測:
  verify_result  pass 2 / needs_changes 1 / fail 0
  done 3 / assign 3 / answer 0 / verifier 1 体

推定パラメータ（sweep にそのまま渡せる）:
  --pDefect 0.3333 --verifierThroughput 2 --coordinatorCapacity 3

注意:
  - 差し戻し率 33.3% を pDefect の下限として使います（見逃した欠陥はボードに現れないため）
  - 検証サンプルが 3 件しかありません。較正には 50 件以上を推奨します
```

**見逃した欠陥は定義上ボードに現れない。** だから観測できる差し戻し率は
真の欠陥率の**下限**でしかない。較正器はこれを隠さず注記する。

推定値をそのまま掃引に渡せる:

```bash
node src/cli.mjs sweep --pDefect 0.33 --verifierThroughput 2 --coordinatorCapacity 3
```

## verifier を増やすべきか

worker を固定して verifier だけ振る。

```bash
node src/cli.mjs verifiers --workers 64 --v 1,2,4,8
```

```
  verifier  ラウンド   品質    正味成果   見逃し   コスト
         1     23.05  0.923     0.923      3.7  $  12.89
         2     21.45  0.932     0.932      3.3  $  13.22
         4     23.65  0.920     0.920      3.9  $  13.71
         8     23.55  0.918     0.918      4.0  $  13.70

  正味成果が最大なのは verifier 2 体
```

検証役も増やせばよいわけではない。**worker 64 体に対して verifier は 2 体**で頭打ちになる。
それ以上は検証そのものがコストとラウンドを食うだけになる。

## コマンド

```bash
node src/cli.mjs sweep [--n 1,2,4,8,16,32,64,100] [--trials 20] [--out out]
node src/cli.mjs verifiers --workers 32 [--v 1,2,4,8]
node src/cli.mjs one --workers 16 [--seed 1]      # 1 走行の詳細
node src/cli.mjs calibrate <board.jsonl> [...]
node src/cli.mjs params                            # 既定パラメータ一覧
```

`--out` を付けると `result.json` / `report.md` / `index.html`（グラフ付き 1 ファイル）が出る。
いずれの出力にも「実測ではない」という断りが必ず入る（テストで固定）。

すべてのパラメータは `--pComplete 0.7` のように名前で上書きできる。
同じ seed なら結果は完全に再現する。

## このモデルの限界

- **タスクの中身を見ていない。** 分解しやすい仕事かどうかは `serialFraction` という 1 つの数字に押し込んでいる
- **混線のモデルが粗い。** 台数の対数に比例して完了率が落ちる、という形を仮定しているだけ
- **欠陥の見逃し率は較正できない。** ボードに現れないため、外部の正解データが要る
- **実際の LLM の挙動（モデル差・プロンプト感度）は入っていない**

次にやるべきは、**実際に 1 体 / 8 体 / 32 体で同じ課題を 3 回ずつ走らせて、
このモデルの逆 U 字が再現するかを確かめること**。再現しなければモデルが間違っている。
